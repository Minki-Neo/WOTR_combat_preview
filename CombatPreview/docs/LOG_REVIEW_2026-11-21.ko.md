## 1. 첫 호버에서 기대 피해가 늦게 보이는 문제

### 확인한 사실

주문 파라미터는 Current 130건, NotObserved 126건, StateChanged 69건입니다. `SpellPreviewRuntime.Describe`는 최신 관측 DC가 없으면 내성 확률을 확정하지 않고, SR도 최신 파라미터가 없으면 비웁니다. 기본 CL을 읽었더라도 최종 DC/SR 입력이 준비됐다는 뜻은 아닙니다.

`ParameterStamp`가 사용하는 `BetaReader.NativeStamp → CountStamp → State`에는 위치·피해량·교전 대상·활성 효과·공격 모드·턴이 포함됩니다. 같은 주문의 DC/CL이 달라졌다는 확인 없이 이 넓은 키가 달라져도 기존 파라미터를 기각합니다.

근거: #16877 → #16878, 환영 살인마, 동일 시전자·대상·능력 인스턴스·턴. 948ms 사이 Current/DC25/기대 HP 감소 59.23125에서 StateChanged/DC 미확인/기대 HP 감소 미확인으로 바뀌었습니다. 입력 문자열의 첫 변경은 시전자 좌표이며 약 9cm의 위치 변화가 있습니다. 다른 상태가 동시에 바뀌었을 가능성까지 배제하지는 않지만, 이 위치 변화만으로도 현재 비교 키는 달라집니다.

이전의 “UI가 재호버 전까지 갱신되지 않는 것 같다”는 가설은 현재 로그에서 입증되지 않았습니다. 코드에는 150ms 주기 자동 갱신이 이미 있으며 같은 대상의 반복 기록도 있습니다. 고정 로그에서 동일 능력·대상·턴의 기대 HP 미확인 → 확인 전환은 0건입니다. 따라서 관측 부재/과도한 캐시 기각은 확인했지만, 사용자가 본 재호버 복구의 정확한 이벤트 순서는 아직 미확정입니다.

### 개선 작업

- [ ] 파라미터 키와 공격/대상/공간 키를 분리한다. 위치 의존 DC/CL 핸들러의 검증 없이 위치만 무조건 삭제하지 않는다.
- [ ] DC·CL·메타매직·랭크 준비 상태의 변화와 갱신 요청 번호를 기록한다.
- [ ] 첫 커서 진입, 대상 변경, 관측 도착, 계산 시작·완료, 표시 시각을 같은 요청 ID로 기록한다.
- [ ] 관측이 도착하면 같은 대상에 커서를 유지한 상태에서도 즉시 재계산을 예약한다. 기존 자동 갱신과 중복 실행을 막는다.
- [ ] 미관측 기본 주문의 DC/CL/SR을 자체 읽기 전용 어댑터로 보강한다. HCO 결과를 넣거나 실제 게임 규칙을 호출하는 방식은 사용하지 않는다.
- [ ] 준비 대기, 실제 미지원, 피해 없음, 면역을 구분해 표시한다.

## 2. 유리·불리 재굴림 확률

### 코드 검토 결과

사용 중인 `BetaModel.BuildCore`의 무기 확률은 d20 1–20을 동일 가중치로 셉니다. 접촉 주문도 `SpellPreviewMath.AttackHit`의 단일 d20을 사용합니다. `SaveFailure`는 기본 내성과 Persistent 플래그를 처리하지만 일반 `ModifyD20` 재굴림을 읽지 않습니다. SR 역시 단일 d20입니다.

별도 `D20` 도우미에는 유리/불리·조건부 재굴림·고정 굴림 등의 분포 계산이 있지만, 그것이 존재한다는 이유로 현행 읽기 전용 미리보기에서 적용된 것은 아닙니다. 관련 도우미는 이전 dry-run 경로에서 사용되며 현행 경로에 연결되지 않았습니다. 실제 판정이나 dry-run을 실행해 이를 해결해서는 안 됩니다.

확인한 HCO 0.4.0의 `OddsCalculator.D20Percent`도 1–20을 열거합니다. 은폐 재굴림 처리는 별도 있으므로, HCO와 일치해도 공격/내성 d20 유리보정까지 옳다는 검증이 되지 않습니다. HCO는 비교 대상으로 유지합니다.

예: 한 번 성공률 p라면 독립 두 번 중 좋은 결과의 성공률은 1−(1−p)²입니다. 50%는 75%가 됩니다. 대상의 내성에 유리보정이 있으면 공격자의 효과 성공률은 낮아집니다. Persistent 같은 강제 재굴림, 수치로 더하는 Luck 보너스, 피해 주사위 재굴림은 각각 별도 규칙입니다.

### 실제 로그의 한계

실제 내성 관측 218건 중 RollHistory가 2개인 기록은 13건이며 모두 persistent=false입니다. 예를 들어 #13294는 [20,13]에서 최종13, #16252는 [20,7]에서 최종7을 사용했습니다. 게임 IL에서 RollHistory가 실제 굴림 결과 목록임을 확인했습니다. 이 사례들을 “좋은 값을 선택한 유리보정 13건”으로 분류하면 안 됩니다. 현재 로그에는 재굴림 소스·부호·조건이 없어 원인을 확정할 수 없습니다.

### 개선 작업

- [ ] 실제 공격·확인 굴림·내성·SR·피해 굴림의 이력, 소스, 재굴림 수/방향, 적용 조건, 최종 선택값을 각각 기록한다.
- [ ] 활성 효과를 수동 판독해 기존 순수 D20 분포 계산기에 연결한다. 효과를 소비하거나 가짜 굴림을 만들지 않는다.
- [ ] 공격자 유리/불리와 대상 내성 유리/불리를 별도로 기대 피해의 해당 확률에 반영한다.
- [ ] 같은 굴림 안의 유리/불리 중첩과 상쇄, 실패/성공 시에만 재굴림, Persistent와의 실행 순서를 게임 코드대로 검증한다. 모든 경우를 단순한 p²로 처리하지 않는다.
- [ ] 기본 확률·재굴림 반영 확률·출처를 상세 로그에 남긴다. 미지원 효과를 단일 d20의 확정값처럼 표시하지 않는다.
- [ ] p=0/0.05/0.5/0.95/1과 자연 1/20, 자동 성공/실패, 복합 내성의 회귀 검증을 추가한다.

## 3. 기대 피해 과대·과소

### 실제로 확인한 후보

같은 주사위식의 최근 주문 대조 후보 12건 중 7건에서, 이글거리는 광선의 미리보기 bonus=0과 실제 bonus=4/6/8이 달랐습니다. 관측 #14025/#14030/#14608/#14615/#14742/#17075/#17078입니다. 해당 성분의 criticalModifier는 null, criticalApplied는 None입니다. 일부에는 별도 bonusTargetRelated=1도 있습니다. 이 고정 보정의 차이는 주사위 운으로 생기는 차이가 아닙니다.

다만 7건 중 #14608/#14615의 association만 TrackedInputsMatchAtFirstRule이며 나머지 5건은 TrackedInputsChangedBeforeFirstRule입니다. 앞의 2건도 첫 규칙에서 추적한 입력 일치이며 모든 게임 조건 인증은 아닙니다. 따라서 누락 보정의 강한 후보로 삼되, 실제 bonus를 그대로 예측에 복사하거나 7건을 모두 완전 일치 조건의 확정 오류로 간주하지 않습니다.

### 검증을 완료했다고 볼 수 없는 이유

- 무기 비교 398건은 InputsChanged 324, AttackModeChanged 35, PairChanged 2, PreviewExpired 37입니다. 유효 조건으로 채택된 정확도 비교는 없습니다. 차이 0건을 정확도 100%로 해석할 수 없습니다.
- 피해 추적 성분 621개에서 감소 후 산술 재구성 차이는 0건이지만 독립적인 미리보기 방어 재실행 비교는 0성분입니다. 실제 관측된 반감/면역/배율 뒤의 산술이 맞는 것과 사전 기대 피해가 맞는 것은 다릅니다.
- HCO의 비교 가능 분류에서 AB 차이 필드 121건, 기본 공격 확률 차이 72건 등이 있습니다. 비교 대상/조건과 확률의 의미가 제한되므로 이 수를 모두 예측 오류로 세지 않습니다.
- 재굴림 누락은 공격자에게 유리하면 기대 피해를 과소, 대상 내성에 유리하면 과대 계산할 수 있습니다. 이것은 코드상 영향 방향이며 이번 로그로 각 효과의 실제 오차 크기까지 확정한 것은 아닙니다.

### 개선 작업

- [ ] 주문 피해 보정의 출처를 기본 고정 보정·주사위당·대상별·조건부·첫 광선/후속 광선으로 나눠 기록하고 독립 판독한다.
- [ ] 단발 피해량과 평균을 직접 비교하지 않고 고정 보정, 주사위/타수, 반감, 면역, 취약, DR, 보호막, 임시 HP 단계를 각각 검증한다.
- [ ] 비교 입력이 달라진 이유를 필드 단위로 남겨 채택 가능한 실전 표본을 확보한다.
- [ ] 즉사·복합 내성·재굴림을 최종 분기 확률에 반영하고 일반 HP 피해·즉사 HP 감소를 별도로 대조한다.
- [ ] 관측된 보정이나 HCO 결과를 답으로 재사용하지 않는다. 출처의 독립 재현이 끝난 범위만 지원 모델로 표시한다.

## 4. 성능

UMM 로그에는 spell-first-target 최대449.845ms인 창이 있으며 해당 구간 GC0=1, maxNoGC=3.753ms입니다(원본 UMM 1044행). 이는 첫 대상 처리 구간에 긴 정지가 실제 존재했다는 근거입니다. 이 값만으로 모드 할당이 GC의 유일한 원인이라거나 사용자 재호버 지연과 같은 순간이었다고 단정하지 않습니다. 최근 세 창은 평균2.705/3.256/2.806ms, 최대3.109/3.370/3.477ms였습니다. 평균 FPS만으로 최초 지연이 해결됐다고 판단하지 않습니다.

- [ ] 큰 상태 문자열·전투 로그 직렬화·상태 복사·HCO 비교·피해 분포의 할당량과 첫 사용 비용을 분리 측정한다.
- [ ] GC 동반 지연과 GC 없는 계산 시간을 별도 보고하고 첫 표시까지의 전체 지연과 연결한다.
