## 2. 제품 목표와 유지해야 할 결정

사용자는 현재 공격에서 표시한 AB·상대 AC·피해식·방어 적용이 실제 판정과 맞고, 그 입력으로 계산한 확률과 기대 피해가 신뢰할 수 있기를 원한다. 실제 피해 한 번이 평균과 같아야 한다는 요구가 아니다.

- 무기: 실행 가능한 공격의 명중률을 가장 잘 보이게 하고 AB·AC·피해 주사위·DR·기댓값을 간략 표에 표시한다.
- 주문: 공격 명중, SR, 내성을 구분하며, 복합 주문은 최종 분기별 확률·주사위·상태 효과를 보여준다.
- 체력: 모드 패널에서 본체/임시 HP와 각각의 기대 소모를 보여준다. 정확한 분포와 평균 상태 근사를 구별한다.
- 화면: 좌측 하단 빈 공간, 주먹 버튼 위, 초상화 경계를 기준으로 배치한다. 기본 화면은 간결하게, 설명과 출처는 상세 보기로 보낸다.
- 독립성: HCO는 참고 구현 및 진단 비교 대상이다. 설치·출력·정답에 의존하지 않는다.
- 미확인: 숫자를 만들기 위해 근거 없는 0, 오래된 캐시, HCO 결과를 넣지 않는다. 이미 아는 부분은 가능한 범위까지 표시한다.
- 안전성: 미리보기 때문에 행동·버프·자원·HP·보호막·난수열을 소비하지 않는다.

**게임 계산을 그대로 다시 실행하는 접근은 현행 해법이 아니다.** 완료된 게임 규칙 결과를 수동 관측하고, 현재 상태에서 읽은 값을 분리된 데이터 모델로 계산한다. 원본에 DryRun이나 예측 클래스가 남아 있다는 이유로 다시 연결하면 안 된다. 자세한 제한은 [안전성 감사](SAFETY_AUDIT.md)에 있다.

## 4. 주요 이슈와 해결 과정

### 4.1 임시 체력, 돌가죽, 소모형 보호막

**문제:** 임시 HP가 있거나 돌가죽 같은 방어가 있으면 기대 피해/체력바를 보류하는 경로가 있었다. 여러 타격에서 보호막 잔량이 바뀌는데 각 타격을 같은 초기 방어로 계산하면 과대 감소나 과소 피해가 생긴다.

임시 HP와 돌가죽을 같은 자원으로 취급하면 안 된다. 현행 게임 판독 근거에서 DR·저항·소모형 보호막 등으로 처리된 최종 피해가 임시 HP를 먼저 소모하고, 잔여분이 본체 HP에 들어간다. 임시 HP가 있다는 이유로 별도 DR을 추가하거나 잔여 피해에 DR을 다시 적용하지 않는다. 돌가죽의 소모 잔량은 HP와 별도의 방어 상태다.

예를 들어 **해당 타격에 적용되는 DR10과 충분한 돌가죽 잔량**, 임시 HP8이 있고 방어 전 피해가20이면, 단순한 해당 방어 모델에서는10 감소 → 임시 HP8 소모 → 본체 HP2 감소다. 임시 HP 처리에서 다시 DR10을 빼지 않는다. 실제 관통·다른 방어 경쟁·난이도 등은 별도 입력으로 판단한다.

**어려웠던 이유:** 명중/치명타/거울상/내성/피해 주사위마다 보호막 소모와 다음 타격의 상태가 달라진다. 보호막을 어느 소스에서 먼저 소모하는지, 상시 DR과 어떤 방어를 선택하는지도 필요하다. 기대 피해 평균만 잔량에서 빼면 분기 사이의 상관관계를 잃는다. 무조건 거절하던 초기 정책과 계산량 한계가 표시 공백으로 이어졌다. 과거 모든 임시 HP 누락을 하나의 원인으로 단정할 수는 없다.

**현재 접근:**

- 읽은 방어·등록 순서·잔량을 복사하고, 지원된 주문 분포에서는 같은 주문의 피해 성분/타격이 그 복사 상태를 공유한다.
- 정확한 계산이 되는 경로를 우선 사용한다.
- 수치 입력은 알려져 있지만 보호막 조합/상태 수 한계로 계산이 비는 지원 경로는 평균 피해·평균 잔량 근사로 전환한다. UI와 로그에 ≈, approximate, basis, 가정을 유지한다.
- 임시 HP는 파란색, 본체 HP는 녹색, 예상 소모는 노란색이다. 즉사는 임시 HP를 피해로 소모한 것으로 세지 않고 해당 최종 효과로 분리한다.
- 무기 HP 표시와 평균 보호막 경로는 근사다. 지원되는 주문 공동 분포의 기대 소모와 혼동하지 않는다.
- 피해식·명중률·유형·잔량 자체가 미확인이거나 보호막 외 미지원 방어가 있으면, 근사 허용을 이유로 임의의 값을 만들지 않는다.

비선형성 예: 방어 후 피해 D가0 또는20으로 각각50%, 임시 HP가10이면 실제 기대 본체 소모는5, 기대 임시 HP 소모도5다. 평균 D=10만 먼저 임시 HP에서 빼면 본체0/임시10이 되어 다르다. 이것이 평균 상태 근사를 정확한 HP 분포로 표시하면 안 되는 이유다.

**남은 과제:** 보호막 근사 오차 측정, 복수 무기/공격자의 실제 순서, 특수 피해 가로채기·동적 방어 제거·복합 버프 수명. 최신 빌드의 임시 HP + DR 관통 + 다중 타격 실전 대조도 필요하다.

근거/코드: [최종 원시 자료](RAW_EVIDENCE.ko.md), [소모형 주문 분포](../src/ProtectedSpellSequenceMath.cs), [평균 보호막 근사](../src/MeanShieldApproximation.cs), [HP 결과 선택](../src/HealthProjectionSelection.cs).

### 4.2 응집 사격: DR은 항상 타격마다 독립적이지 않다

아루샬레 관련 제보에서 전력 공격의 각 발에 DR을 반복 적용하면 기대 피해가 너무 작아질 수 있었다. 0.5.50에서 AddClusteredAttack의 대상·전력 공격·무기 유형 조건을 읽어 고정 물리 DR을 누적 예산으로 처리했다. 실제 막힌 양만 그 예산을 소모하며, 빗나감이나 거울상 타격이 본체 DR을 소비하지 않도록 한다. 단일 공격은 일반 DR 경로다.

응집 사격과 소모형 보호막의 결합은 단순 고정 DR보다 복잡하다. 이후 보호막 근사 경로에서 보강한 범위가 있으므로 과거의 “결합 미지원”을 모든 현행 경로에 그대로 적용하지 않는다. 반대로 평균 상태 처리를 모든 공격 순서의 정확한 해법으로 주장하지 않는다.

**교훈:** 특기 이름마다 최종 피해를 덧대기보다 엔진이 등록한 능력과 적용 범위·소모 규칙을 모델링해야 한다. 고정 DR 예산, 돌가죽 잔량, 임시 HP를 서로 다른 상태로 유지한다.

근거: [구현 목록 0.5.50/52](IMPLEMENTATION_CHECKLIST.ko.md), [DR/거울상 등 공통 수학](../src/MitigationMath.cs).

### 4.3 피해식 자체가 틀린 원거리 폴백

0.5.48의 아루샬레 사례는 미리보기1d8+14 / AB+24, 뒤의 실제 공격 비교3d6+22 / AB+25였다. single/fullAttack, 관통 강화, 적용 DR도 달랐다. 실제 피해40/33/32가 평균보다 컸다는 것보다 **주사위·고정 보정·공격 모드가 다르다**는 것이 중요한 증거였다.

원인은 관측 수치가 없을 때 Blueprint 기본 주사위를 그대로 쓰고 원거리 피해 능력치를0으로 보던 폴백, 비중첩 유형 AB의 미지원 등이었다. 0.5.49에서 피해 능력치/배율 대체, 캐시된 크기와 무기 크기 변화, 엔진 크기 표의 복사/조회, 유형별 보정과 예약 효과의 순증분을 보강했다. 매 호버마다 전체 크기 표를 복사하지 않도록 했다.

0.5.67에서는 자연/비무장 등에 적용되는 장비·활성 강화, 관통용 EnhancementTotal, 주적의 가장 큰 일치 보너스와 음수 레벨 CL 감소를 추가로 판독했다. 대상 종속 무기 결과를 공통 캐시에 저장해 다른 대상에게 보너스가 새는 경로도 차단했다.

**주의:** diceBase는 최종 크기 보정 주사위가 아닐 수 있다. 실제 피해식 대조는 diceModified를 우선 확인한다. 조건이 바뀐 사례에서 실제 보정치를 그대로 예측에 복사하면 원인이 감춰진다.

### 4.4 거울상·은폐·군체·반감 누락

AC만 통과할 확률과 최종 본체에 피해를 줄 확률은 다르다. 거울상이나 은폐를 생략하면 AC 명중률은 비슷해도 기대 피해가 높아진다. 같은 대상의 연속 공격에서 거울상이 소모되는 확률도 후속 공격에 영향을 준다.

현재는 AC 기준 확률, 가시성 실패, 거울상/근소 빗나감과 소모를 구분해 기록하며 지원된 연속 모델에 연결한다. 여러 무기의 표시 순서와 실제 실행 스케줄은 같다고 인증하지 않는다. 모든 투명화·감지·은폐 조합을 이름별로 완전히 지원한다는 뜻도 아니다.

군체는 단순 DR 수치가 아니다. 크기/전용 특성에 따른 물리 면역·반감·범위 취약과 치명타 면역을 별도로 처리한다. 물리 면역을 이유로 무기에 붙은 에너지 피해까지 없애면 안 된다.

0.5.47–48에서는 범위 피해 반감과 에너지 퍼센트 보정의 단계/내림/최소 피해를 공통 피해·분기·보호막·HP 및 캐시 키에 함께 연결했다. 평균값에 마지막으로 배율을 곱하는 방식은 주사위별 반올림·최소 피해·DR과 일반적으로 같지 않다.

근거/코드: [군체 규칙](../src/SwarmRules.cs), [명중 후 회피](../src/AttackConcealment.cs), [에너지 배율](../src/SpellEnergyScaling.cs), [공통 피해 수학](../src/DamageMath.cs).

### 4.5 환영 살인마: 복합 내성을 한 확률로 뭉개면 안 된다

초기에는 의지 실패율, 인내 미확인, 3d6 기본 평균을 긴 설명으로 나열해 최종 효과를 읽기 어려웠다. 같은 주문이 반복해서 미확인으로 나온 원인은 하나가 아니었다. 조건부/후속 DC, 불운 소모, 런타임 참조 GUID, 특수 매개변수 핸들러, 활성 메타매직 로드 등 서로 다른 단계의 문제가 있었다.

현재는 지원되는 트리에서 SR → 의지 → 인내 → 즉사/주사위 피해/효과 없음의 **최종 분기**를 구성하고 표로 표시한다. 의지 실패 뒤 소모된 효과가 인내에 그대로 남아 있다고 가정하지 않고 지원된 수명 변화를 전달한다.

상태 변화가 없다는 단순 예에서 SR 통과 s, 의지 실패 w, 인내 실패 f라면 즉사 확률은 s×w×f, 인내 성공 시 피해 분기는 s×w×(1−f)다. 실제 소모 효과가 있으면 f는 앞 단계에 도달한 상태에 조건부인 확률이다. 서로 독립인 단일 내성 확률 두 개를 무조건 곱하면 안 된다.

즉사의 HP 감소 기여도는 해당 즉사가 적용되는 최종 분기에서 대상의 남은 본체 HP를 기준으로 한다. 이를 보통 주사위 피해 평균이나 임시 HP 흡수와 합쳐 설명하지 않는다. 면역·추가 조건이 미확인이면 전체 즉사율도 확정하지 않는다.

0.5.54의 구체 원인은 Blueprint 참조가 역직렬화 후 문자열 guid를 비우고 deserializedGuid를 보존하는데, 기존 판독이 비워진 문자열에 의존한 것이다. 공통 런타임 GUID 판독을 수정했다. 0.5.55 기록에서는 0.5.54 실행 로그의 불운 소모 계산과 HP 예상을 확인했다. 이것이 모든 즉사 확률의 실전 인증은 아니다.

0.5.66의 다른 미표시 사례는 MetamagicRodMechanics 미지원으로 DC가null이 된 것이었다. 0.5.67–68에서 로드와 기본 AutoMetamagic 공통 조건, 선택 메타매직 슬롯 비용을 독립 판독했다. 같은 “환영 살인마 미확인”이라도 누락 단계와 원인 코드를 먼저 확인해야 한다.

### 4.6 유리보정과 HCO: 일치가 정확성의 증거는 아니다

0.5.42 검토에서 D20 보조 수학 함수는 있었지만 현행 무기·접촉·SR 확률 경로에는 일반 ModifyD20 재굴림이 연결되지 않았음을 확인했다. 코드가 존재하는 것과 제품 경로에서 사용되는 것은 다르다. 당시 확인한 HCO의 기본 D20 계산도 이 모든 효과를 인증하는 기준이 아니었다.

0.5.44 이후 활성 효과의 첫 굴림 조건·재굴림 방향·유리/불리 상쇄·사후 굴림·자연1 치환을 독립 모형에 연결했다. Persistent의 성공 시 재굴림, 공격자의 유리한 굴림, 대상의 내성 유리보정, 고정 수치 Luck 보너스, 피해 주사위 재굴림을 구분한다.

단순 독립 유리보정은 성공률 p를 1−(1−p)²로 바꾸지만, Persistent와 소모 효과까지 모두 이 식 하나로 계산할 수는 없다. 실제 RollHistory가 두 개라고 무조건 좋은 값을 고른 유리보정으로 분류해서도 안 된다. 소스·조건·방향·최종 선택값을 확인한다.

HCO 진단은 선택적 참고 경로이며 authority=ReferenceOnly, probabilityEquivalenceVerified=false다. 지속 메타매직/유리한 마법/후속 내성이 HCO와 다르다는 이유로 자체 계산을 HCO에 맞추지 않는다. 확인된 게임 의미와 독립 주사위 열거로 검증한다. 참고 구현을 공부할 때는 계산 단위·상태 읽기·판정 순서를 이해하고, 코드를 가져온다면 라이선스를 별도 확인한다.

근거: [0.5.42 실제 검토](LOG_REVIEW_2026-11-21.ko.md), [D20 모형](../src/D20RollModel.cs), [비교 어댑터](../src/OverlayReference.cs).

### 4.7 정의의 번개: 주문별 예외보다 공통 액션 해석

이 주문이 보이지 않던 원인은 “특이한 주문 이름을 등록하지 않아서”가 아니었다. 직접 내성 탐색 깊이4와 연결 효과가 공유하던 예산, 조건부 액션을 단순 피해 후보로 모으던 방식, 지연 전달 거절, 선택 주문/대상 판독, 관측되지 않은 CL, 후속 상태 내성 실패가 앞의 피해까지 지우던 결함이 겹쳤다.

0.5.39에서는 직접 탐색을 깊이12/512노드로 제한하고 연결 효과 예산을 분리했다. 대상/시전자 특성·성향·직업 조건으로 실행 분기를 선택하고, 명중 굴림을 요구하지 않는 지연 전달을 지원했다. 실제 27개 액션 구조로 이전 한도의 실패와 새 탐색 완료를 회귀 검사한다.

중요한 의미 차이: 이 주문의 피해 자체에는 공격 명중 굴림/SR이 없고, 뒤의 반사 내성은 상태 효과를 결정한다. 반사 실패율을 피해가 들어갈 확률처럼 곱하면 틀린다. 귀를 찢는 비명 등도 내성 성공/실패의 피해·상태 분기를 분리해야 한다. 후속 내성만 미확인이고 어느 분기에서도 앞의 피해가 같다면 그 피해 계산은 유지할 수 있다.

0.5.59에서는 적 전용 광역기의 아군이 후보/계산 큐/32명 제한을 차지하던 경로를 수정했다. 적/아군 관계 필터는 대상 제한 전에 적용하고, 호버 대체 경로가 제외된 아군을 다시 넣지 못하게 했다. 아군도 맞는 광역기는 유지한다.

주변 무작위 전파는 별도다. 0.5.58은 끔찍한 웃음의 직접 판정까지 통째로 버리던 문제를 고쳤지만, 주변 무작위·재귀 전파의 전체 HP 영향을 계산한 것은 아니다. 부분 결과는 “주 대상 직접 판정” 범위로 표시한다.

### 4.8 첫 호버/재호버 대기와 HP바 누락은 서로 다른 문제다

0.5.42에는 같은 능력·대상·턴에서 약9cm의 시전자 위치 변화만으로도 넓은 상태 키가 달라져 최신 DC/CL을 버릴 수 있는 사례가 있었다. Current→StateChanged가 확인됐지만, 사용자가 본 재호버 복구의 정확한 이벤트 순서까지 그 로그로 확정되지는 않았다.

적용한 보강은 세 층이다.

1. 지원된 위치 비의존 DC/CL 핸들러는 파라미터 의존성 키를 사용하고, 미지원/공간 의존 가능성이 있는 핸들러는 엄격한 키를 유지한다. 최초 관측 전의 일반 주문책 계산도 지원 범위에서 독립 판독한다.
2. 새 매개변수 관측이 도착하거나 호버/revision이 바뀌면 처리한 대상도 우선 재계산한다. 무조건 캐시 수명을 늘리거나 모든 상태 필드를 키에서 삭제하지 않는다.
3. HP 선택의 else-if/null 경로가 유효한 전체 분기 결과를 가리던 문제를 수정했다. 전체 기대 피해만 알려진 지원 경로는 평균 HP 근사를 명시하고, 작은 양수 색상 구간에는 최소 표시 폭을 준다. 실제0이나 미확인 피해에는 색을 꾸며 넣지 않는다.

**교훈:** “늦게 뜬다”를 파라미터 준비, 큐 대기, 분포 계산, 결과 선택, 레이아웃/렌더링 단계로 나누고 같은 요청/프레임에서 대조한다.

### 4.9 행동 가능 여부와 UI 공간

기습 라운드에는 일반 이동과 공격을 모두 할 수 없으므로 풀어택 설정만으로 공격열을 만들 수 없다. 초기 IsAttack 판독은 “예정된 공격 행동이 있는가”와 “남은 표준 행동으로 공격 가능한가”를 혼동했다. 현재/예정 행동, 대상·사거리·접근 필요·기습 여부를 읽고, 지원되는 일반 기습 공격은 단일 공격으로 다룬다. 실제 행동/경로 예측을 새로 실행하지 않는다.

Overused는 CPU 계산 한도 초과가 아니다. 엔진의 선택 행동 계획 불가/소모 상태와 관련된 플래그다. 사거리에서 이동 없이 가능한 표준 공격은 알려진 조건 아래 별도 추정할 수 있지만, Lost/Used인 일반 행동을 실행 가능으로 바꾸면 안 된다. 0.5.65의 합계 제외 참고 행은 패널을 키웠고, 사용자 요청으로 0.5.66에서 제거했다.

UI에서는 긴 이름이 명중률 열을 침범하지 않도록 배치하고 한글 받침이 잘리지 않게 텍스트 높이/줄바꿈을 다뤘다. 명중률은 우측 강조, 상세 설명은 접기, 초상화 경계와 좌측 빈 공간을 우선한다. 새 기능을 늘릴 때 숫자 열보다 설명이 화면을 차지하지 않도록 한다.

기본 게임 적 HP바에 예상 피해를 얹는 실험은 호스트 표시/숨김·풀링·연결과 게임 자체 보정 곡선에 영향을 받았다. 최대 HP/부상/기습에서 보이거나 안 보였다는 사용자 관찰만으로 단일 원인을 확정하지 않는다. **0.5.63에 기본 HP바 탐색·오버레이·LateUpdate·설정 경로를 제거했고, 모드 패널만 유지하기로 했다.** 이 결정을 모르는 후속 개발자가 삭제한 경로를 복원하면 같은 문제가 반복된다.

### 4.10 주문서와 메타매직의 별도 파라미터 경로

주문서 환영 살인마가 미확인인 사례는 일반 주문책 판독기가 아이템 출처를 거절했기 때문이었다. 게임의 CalculateParams는 아이템일 때 GetParamsFromItem에서 조기 반환하며 일반 주문책 보정을 통과하지 않는다.

0.5.65에서 제작 DC/CL, ScrollMastery/전문화, 완드·물약, 아이템 유형별 CL, 제작 메타매직 등의 우선순위를 별도로 구현했다. 일반 SpellFocus/AddCasterLevel을 아이템에 중복 적용하면 안 된다. 저장된 원본 OverrideParams, 문맥 교체, 일반 주문책, 아이템은 출처/우선순위를 구분한다.

0.5.68은 기본 AutoMetamagic 공통 조건을 일반 주문과 아이템에 연결했다. 엔진처럼 아이템에는 로드/다음 주문 등록을 건너뛴다. 임의 파생 AutoMetamagic, MagicHackData 조건, 읽히지 않은 부모/주문 목록과 MetamagicOnNextSpell은 여전히 별도 미확인 사유가 있다.

### 적용한 계산 효율 정책

- **조기 제외:** 대상 없는/반복 공격 관측 중 불필요한 캡처를 먼저 걸러낸다. 적 전용 범위기의 아군을 큐/제한 전에 제외한다.
- **대상 분산:** 한 프레임 최대2명, 3ms soft budget. 첫 대상은 진행하고 대상 한 명의 계산 중간을 중단하지 않으므로 3ms hard cap이 아니다.
- **갱신 묶음 안 재사용:** 같은 시전자 상태·학파·D20 출처·파라미터 등을 ScopedReadMemo로 공유한다. 0.5.58에는 SchoolInputs의 Begin 스코프 누락 때문에 재사용이 실제로 꺼져 있던 것도 수정했다.
- **안전한 장기 캐시:** FieldInfo·기존 객체의 식별 토큰·표현용 불변 문자열·유효한 HUD 참조 등과 살아 있는 전투 수치 캐시를 구별한다. HUD는 유효하면 재사용하고 배치 위치는 현재 값을 읽는다.
- **완전한 숫자 키의 분포 재사용:** 방어 수치·잔량·등록 순서·HP·주사위/확률 등이 같은 보호막 계산을 재사용한다. 예산 실패 결과도 재사용해 같은 호버에서 비싼 실패를 반복하지 않는다.
- **직렬화 전 제한 검사:** 기록하지 않을 큰 JSON을 먼저 만들지 않는다. 표시/실제 판정/성능 예산을 분리하고 누락 수를 남긴다.
- **유한 상태와 근사:** 지원된 주문 공동 분포는 연산 예산250,000 등의 상한을 둔다. 평균 보호막 주문 근사에도 성분/전달/소스 상한이 있다. 상한을 무작정 올리는 것은 기능 수정이 아니라 성능 위험 증가다.
- **계측의 분리:** 전체 게임 프레임, 첫 표시 지연, 단계별 비용, GC 동반/비동반, 할당량을 함께 본다. 중첩 단계 시간은 합산하지 않는다.

**후속 작업:** 대상별 최대값/할당량, 무기·주문 첫 사용 비용, 로그 ON/OFF와 HCO 참고 비교 ON/OFF의 같은 조건 측정. 단일 대상이 비싸면 추가 분할/증분 계산 또는 더 제한된 정확 계산이 필요하다. 작업 스레드로 Unity/게임 객체를 읽는 방식은 검증된 해결책으로 취급하지 않는다.

## 6. 정확도를 검증하는 장치와 분석 원칙

### 결정적 입력부터 대조한다

실제 한 번40 피해가 표시 기대42와 다르다는 이유로 오류가 되지는 않는다. 대신 다음을 대조한다.

| 항목 | 대조할 내용 |
|---|---|
| 명중 | 같은 공격 유형/조건의 최종 AB, 적용 AC, 실제 D20/재굴림/자동 판정 |
| 피해식 | 최종 diceModified, 타수, 고정/대상별/주사위당 보정, 추가 성분, 치명 배율 |
| 방어 | 관통 조건·실제 적용 감소량·반감·면역·취약·소모성 방어의 출처/순서 |
| 주문 | DC·CL·RankBonus·메타매직·SR, 각 후속 내성의 조건부 상태 |
| HP | 최종 규칙 피해와 본체/임시 HP 감소를 구별. 전체 공격열과 단일 타격을 구별 |

예를 들어 AB+5/AC10, 일반 단일 d20, 별도 빗나감 없음이면5 이상 성공이므로80%다. AC10이라는 수치만으로 어떤 명중률이 틀렸다고 할 수는 없다. 같은 상태의12d6+12 예측과 실제12d6+10은 피해식 입력의 차이이며, 주사위 운으로 설명할 수 없다. 그 차이가 계산 결함인지 시전/버프/공격 모드 변화인지는 연결된 입력으로 판단한다.

### 현재 기록과 한계

0.5.61부터 최종 판정의 AB/AC·보정 출처·피해식·실제 감소·완료 시 방어 등록을 구조화했다. 0.5.64는 표시한 HP 입력을 불변 보존하고, 0.5.68은 공격 명령의 AttackHandInfo.Rule과 실제 규칙 객체를 대조해 무기별 타격 행을 연결하며 inputAtAttackBegin을 보존한다.

같은 행이라는 사실은 같은 전투 조건이라는 뜻이 아니다. InputsChanged/PreviewExpired/AttackModeChanged/PairChanged는 계속 유효한 거절 사유다. 과거 0.5.42의 무기 비교398건이 모두 제외됐으므로 “오류0건=정확도100%”라고 할 수 없었다. 행 연결을 보강한 목적은 분모를 확보하고 원인을 분리하는 것이지 검사를 느슨하게 하는 것이 아니다.

원시 데이터도 전지적 기록은 아니다. 최종 DR 등록 목록은 실제 적용 DR과 다르고, 완료 시 잔량은 피해 직전 잔량과 다르다. 엔진이 보존한 AtTheMoment 값과 완료 시 캐시 값도 구분한다. 별도 중간 스냅샷 없이 실제 임시 HP 흡수량을 최종 피해값만으로 역산하지 않는다.

현재 원칙은 **중간 방어 스냅샷을 계속 추가하기보다 최종 판정과 이미 표시/판독한 입력을 보존**하는 것이다. 동적 핸들러 내부의 모든 상태를 기록한다고 주장하지 않는다. captureFailure·누락/잘림·한도·rate limit·로그 회전과 세션을 함께 확인한다.

실전 확인의 좋은 사례도 범위를 제한해야 한다. 0.5.57 실행의 유효 매개변수 대조186건에서 DC/CL/RankBonus가 모두 일치한 것은 세 매개변수의 해당 표본 근거다. 고유 시전186회, 전체 피해·확률·모든 주문의 인증은 아니다.

남겨야 할 정책: 계산 불가 대신 근사가 허용되는 것은 **알려진 수치로 정의된 제한적 모형**이다. 미확인 입력을 임의의 값으로 채우는 정책이 아니다. UI의 미확인에는 가능한 짧은 사유/원인 효과를 보여주고 상세 로그에 입력 부족을 남긴다.

## 9. 이어서 작업하는 절차

1. 현행 버전/커밋, 실제 실행 로그 버전·세션·보존 구간을 먼저 확인한다. 새 문서의 검사 결과를 구버전 로그에 소급 적용하지 않는다.
2. 재현 한 건을 미리보기→공격/시전 시작→최종 규칙/피해에 연결한다. 동일 조건 비교와 후보를 구분한다.
3. 값이 비면 선택/대상/행동/파라미터/내성/피해 분기/보호막 예산/HP 결과 선택/UI 중 어느 단계인지 먼저 찾는다.
4. 해당 게임 컴포넌트/필드/순서를 로컬 제공 DLL·로드된 정의로 조사한다. 이름별 예외보다 공통 컴포넌트 어댑터로 해결하고 순수 데이터 계산과 분리한다.
5. 해당 결함을 드러내는 회귀 사례를 추가한다. 코드/테스트 함수가 현재 실행 경로에 연결됐는지도 확인한다.
6. 의존성 키·동일 배치 스코프·null/실패 캐시·연산 한도·진단 필드·분석기까지 함께 검토한다.
7. 구현 완료, 자동 검사, 실제 게임 검증, 남은 제한을 따로 기록한다.
8. 단계별 커밋에는 증상/원인/변경/검증을 남긴다. 버전별 ZIP만 만들고 소스 커밋을 미루지 않는다. 릴리즈/중앙 등록/설치가 필요한지는 작업 지시 범위에 맞춘다.

저장소 루트 기준 기본 명령:

~~~powershell
dotnet run --project CombatPreview/tests/CombatPreview.Tests.csproj -c Release
dotnet run --project CombatPreview/tests/ReferenceLayout -- "<GameDir>/Wrath_Data/Managed"
python CombatPreview/tests/damage_trace_analysis_test.py
dotnet build CombatPreview/CombatPreview.csproj -c Release "-p:GameDir=<GameDir>" -p:ResolveAssemblyReferenceIgnoreTargetFrameworkAttributeVersionMismatch=true
~~~

GameDir는 사용자가 제공한 실제 설치 경로로 바꾼다. SDK/게임/UMM 참조 환경과 복원 상태에 따라 초기 설정이 필요하다. 게임 참조 DLL을 저장소에 추가해 빌드를 편하게 만드는 방식은 사용하지 않는다.

실전 분석은 [한 세션 검증 절차](SINGLE_SESSION_REVIEW.ko.md)를 따른다. 현재 JSONL과 .prev를 함께 보존하고 세션·순번·원본 범위를 구분한다. 원시 로그와 사적 분석 파일은 Git에 올리지 않는다. 누락된 과거 로그를 새 코드로 소급 복원할 수는 없다.

0.5.68 기준 기록된 자동 검사: C#26,493 단언 + 27-action 주문 회귀, 제공 게임 메타데이터291항목, Python 분석26 tests, Release 빌드 및 설치 ZIP 검사. 이 문서는 그 검사 이력을 설명하며 게임 실행/FPS 검증을 새로 완료했다는 보고가 아니다.

## 10. 다음 개발자가 특히 기억할 인사이트

- “값이 틀리다”와 “값이 늦다/없다”는 별도 결함일 수 있다. 입력 준비와 표시 결과 선택을 분리해 계측한다.
- 피해 평균 하나로는 소모성 방어·거울상·내성 소모·임시 HP의 순차 상태를 표현할 수 없다.
- 정확한 분포를 무한히 확장하면 호버가 게임을 멈출 수 있다. 상한·실패 재사용·조건부 근사는 제품 동작의 일부다.
- 캐시는 저장하는 것보다 **무엇이 바뀌면 버려야 하는지**가 중요하다. 잘못 넓은 키는 지연, 잘못 좁은 키는 오답을 만든다.
- 일부 후속 효과를 모르더라도 독립적인 앞의 피해/직접 판정을 보존할 수 있다. 부분값을 전체값으로 광고하지 않는 것이 조건이다.
- “같은 주문 미확인”의 원인은 매번 같지 않다. 세부 실패 코드와 활성 출처를 먼저 찾는다.
- 엔진이 이미 합산한 보너스를 독립 어댑터가 다시 더하지 않는다. 대상 없는 캐시에 대상별 값을 섞지 않는다.
- 로그의 후보 수·대상 수·호버 수는 고유 시전 수가 아니다. 동일 조건 비교0건에서 오류0건은 정확성 근거가 아니다.
- HCO와의 일치도, 실제 굴림 뒤 산술 재구성 성공도 전체 사전 확률/기대 피해의 인증이 아니다.
- 오래된 이관 문서와 “구현 완료” 체크박스를 제품 사실로 간주하지 않는다. 현행 경로와 실제 실행 버전을 확인한다.
- UI도 계산 예산을 소비한다. 전체 장면 탐색·동일 문자열/GUIContent 생성·버릴 JSON 직렬화를 고빈도 경로에서 반복하지 않는다.
- 실패 사유/근사 가정을 남기는 기능은 임시 메모가 아니라 다음 오류를 해결할 관측 장치다.
